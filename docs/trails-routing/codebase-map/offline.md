# offline

## Summary
The offline "Download this fire" system is built entirely in the app. It is not a service-worker cache, and it has three parts. (a) frontend/src/offline/packModel.ts is pure and tested. buildPackPlan(PackInputs) lists every absolute URL a pack needs as PackFilePlan {url, immutable, estBytes, optional?}. The sources are the snapshot JSONs (always mutable), perimeter versions, hotspot day chunks, ToA tifs, capped HRRR frames and wind grids, incident-map previews, and z/x/y raster tile pyramids. The pyramids come from sheetTileUrls({url_template,minzoom,maxzoom,bounds}), which enumerates the full rectangular slippy grid and wraps each URL in dataUrl(). (b) frontend/src/offline/packs.ts runs the download. Phase 1 fetches the catalogs and manifests with rawFetch, the un-wrapped fetch, to build PackInputs. Phase 2 runs 6 concurrent fetchInto calls. Each one buffers the whole response with res.arrayBuffer() and writes it atomically to OPFS. Immutable files that are already stored are skipped. Any failure of a non-optional file fails the whole pack. After the files, it writes packs/{slug}/pack.json with the url -> filename map plus prefix fallbacks, prunes files no longer referenced, and re-indexes the pack in memory. (c) packs.ts also serves the pack. installOfflineFetch replaces window.fetch, and only on the main thread. For GET requests it looks up an in-memory Map keyed by the exact URL string: string input verbatim, URL.href, or Request.url. Query strings are part of the key, and the only exception is the open-meteo prefix list. When offline it tries the pack first. When online it tries the network first, and for packed URLs it gives up on the network after 8 s. It falls back to the pack on a non-ok response or a thrown error. The pack response is always status 200 with the whole file, read fully into memory. Its only headers are content-type, derived from the filename extension (default application/json), and x-rd-offline:1. The wrapper never reads the request's headers, so Range is ignored. The service worker built by scripts/build-sw.mjs only precaches and serves same-origin app-shell assets. Cross-origin B2 and fire-api data is never touched by it. React Query uses networkMode 'always' so queries still run offline and reach the wrapper. A fire counts as offline-available when store.offline.packs[fire_slug] exists, hydrated at boot from pack.json. The directory, the OfflineFiresStrip and the OfflineCard all key off this. Existing layers read offline data by calling main-thread fetch with the same URL strings the plan produced. The plan uses the same resolver functions as the layers, and PackImg exists because <img> bypasses the wrapper. MapLibre raster and image sources work because MapLibre fetches them on the main thread through global fetch with a Request object. MapLibre vector-tile and GeoJSON-URL sources are different: they are fetched inside MapLibre's own web worker with that worker's fetch, so the window.fetch wrapper never sees them. Today every GeoJSON overlay is fed in-memory data, so nothing breaks. A new 'vector' trails source with https tile URLs, however, would NOT be served offline. The offline map style (MapRoot) is a single background layer with no sources, glyphs or sprite. Line layers render on it. Text labels fall back to locally drawn glyphs because MapLibre draws glyphs itself when the style has no glyphs URL. Conclusions: (1) a z/x/y vector pyramid can be packed by reusing sheetTileUrls, but the vector source needs a custom addProtocol scheme whose main-thread handler calls window.fetch with the exact https pack URL. In addition, either the worker uploads the full rectangular grid, or the plan enumerates from a published tile list or marks the tiles optional. (2) A PMTiles file read with HTTP Range CANNOT be served offline today. Every pack fallback returns a full-body 200 without Content-Length, which pmtiles' FetchSource rejects, and opfs.ts can only read whole files. It needs either Range-aware serving (206 + Content-Range + Content-Length via OPFS File.slice) or, cleaner, a custom pmtiles Source that reads OPFS directly. (3) A binary graph and a GeoTIFF cost grid work with NO changes to the wrapper, as long as they are fetched whole, on the main thread, by the exact planned URL. That means fetch -> arrayBuffer -> geotiff fromArrayBuffer, then transfer to the routing Web Worker, and never geotiff fromUrl or a fetch from inside the worker. The plan needs new PackInputs fields, a Phase-1 fetch of the per-fire descriptor JSON, versioned immutable URLs, and cosmetic extension/content-type additions.

## Conventions
- Keep planning pure and unit-tested in packModel.ts: no fetching and no storage (file header 1-4). Put fetching and OPFS in packs.ts and opfs.ts, which have no tests. Tests are vitest in a node environment and only match src/**/*.test.ts (frontend/vite.config.ts:25-28).
- Plan URLs and runtime URLs must come from the SAME resolver function (packModel.ts:192-195; spreadToaUrl, weatherImageUrl and windUvUrl are shared). setSpreadArchiveBase is called in runDownload so the planned URLs match the runtime ones (packs.ts:279-280). The wrapper matches exact strings.
- Catalogs carry root-relative paths resolved via dataUrl() (api/catalogs.ts:58-60). Perimeter paths are used VERBATIM, never reconstructed (packModel.ts:149-150; fireApi.ts:57-64).
- immutable:true means 'skip if a file with this name is already stored' (packs.ts:201-204). Only use it for content under versioned or run-stamped URLs (hotspot `g{gen}` at packModel.ts:166-176, run-stamped ToA and frames). Mutable content (snapshots, today's hotspot chunk) is immutable:false and is re-downloaded on every Update.
- optional:true is only for best-effort content where a 404 is normal (weather frames, packModel.ts:30-33, :204). Otherwise 'A pack with silent holes is worse than a failed download' (packs.ts:353-355).
- Downloads must use rawFetch or rawJson, never the wrapped fetch (packs.ts:113-117, :261-262).
- New catalog fields are optional and guarded, because older or CDN-cached catalogs omit them (types.ts:114-117).
- Every map source and layer id is prefixed 'rd-'. Only rd- sources and layers survive basemap swaps (MapRoot.tsx:146-157). Layers use beforeIdFor for z-order (incidentMapLayer.ts:79).
- Any byte loader that bypasses fetch (<img>, Image(), a Web Worker's fetch, MapLibre's worker, geotiff fromUrl) bypasses the offline pack. Existing code works around this explicitly: PackImg.tsx:1-6 and weatherLayers.ts:79-84.
- The owner wants minimal npm dependencies and Python/GDAL-CLI worker tooling. A pmtiles dependency, which brings fflate, must be justified against the no-dependency z/x/y option or a small hand-written PMTiles v3 reader.
- Comments explain why, often citing measured data (EST sizes 'measured from live Big Grass data (2026-08)', packModel.ts:45).

## Risks
- Vector tiles bypass the offline layer. A MapLibre 'vector' source with https tiles is fetched in MapLibre's worker, so window.fetch is never consulted. Offline, every trail tile fails even when it is in the pack. Fix with an addProtocol scheme that calls window.fetch on the main thread, or use per-fire GeoJSON with setData. The same applies to any geojson source given a URL string instead of data.
- Web Worker fetches are not wrapped. The routing Web Worker must not fetch() its graph or grid by URL. installOfflineFetch patches window.fetch only (packs.ts:125-128), and the SW ignores cross-origin requests (build-sw.mjs:94). Fetch on the main thread and transfer the buffer, or read OPFS directly in the worker.
- PMTiles needs new serving code in either case. Range emulation must also avoid reading the whole file per request (opfs.ts:69 reads it all). Option B, a custom Source, needs an exported pack lookup and likely the pmtiles npm dependency plus fflate, which conflicts with the minimal-deps preference unless a small reader is written. The PMTiles file must be versioned and immutable: a pack copy that differs from B2's current bytes at the same URL, mixed online and offline, corrupts reads. The ETag check only fires when both ETags are present, and pack responses carry none.
- sheetTileUrls assumes the full rectangular grid exists (packModel.ts:75). GDAL MVT and tippecanoe skip empty tiles, so B2 would 404 and a non-optional plan entry fails the entire pack download (packs.ts:353-355). Options: the worker uploads empty tiles for the whole grid, the descriptor publishes the list of existing tiles and the plan enumerates from it, or tiles are marked optional. Optional also silently tolerates real network errors, which hides holes.
- An exact-string URL match means any difference between the plan URL and the runtime URL (encoding, trailing slash, query order, cache-buster, relative vs absolute) silently misses the pack. MapLibre passes Request objects whose .url is absolute and normalized, while pack keys are raw strings. With the relative dev DATA_BASE_URL ('/data'), keys are relative but MapLibre's Request.url is absolute, so packed tiles will not match in dev or local static builds unless VITE_DATA_BASE_URL is absolute. Test offline with an absolute data base, or normalize keys with new URL(url, location.href).href on both the index and lookup sides.
- Removing a pack can hide another pack's files. URLs shared across packs map to whichever pack was indexed last (packs.ts:67-69). unindexPack deletes every entry pointing at the removed slug (packs.ts:75-80), so removing pack B unindexes shared URLs that pack A also stores until the next reload. This already happens with catalog.json and the fires index. It gets worse if trail tiles come from a shared national pyramid that overlaps two fires.
- immutable:true only checks that a file with that name exists (packs.ts:201-204). If graph, grid or tile URLs are not versioned per build, an Update keeps stale routing data forever. Put a rev or hash in the path, or mark the file immutable:false.
- Large files are buffered fully in memory twice: on download (res.arrayBuffer() at packs.ts:207) and on every pack serve (opfs.ts:69). This is fine for a few-MB graph or grid. It is a problem for a PMTiles file of tens of MB on mobile, and a disaster if a PMTiles file were served per tile request through readPackFile.
- The pack index hydrates asynchronously (main.tsx:41 void initOfflinePacks()). Requests issued offline before hydration pass straight to the network and fail. React Query's retry:2 usually recovers, but a routing loader outside React Query should retry or await readiness.
- Progress is counted per file. A single large PMTiles, graph or grid file shows no byte progress until it completes (packs.ts:346, :358). With thousands of vector tiles, the per-file sha256 plus the OPFS createWritable round-trip dominates. That is acceptable, since incident-map raster pyramids already do this.
- B2 content headers: the worker config has no .pbf/.pmtiles/.bin/.tif content types (config.py:214-229) and never sets ContentEncoding (b2.py:135-139). Gzip-compressed MVT uploaded without Content-Encoding breaks MapLibre both online and in the pack, because fetch only auto-decompresses when that header is present. Write COMPRESS=NO tiles or set ContentEncoding.
- Offline, the version pointer must itself be packed. The app reads the catalog, manifest and descriptor from the pack's snapshot copies, so the per-fire descriptor must be added to snapshotUrls. Otherwise the offline app cannot discover the graph, grid or tile URLs, or it discovers a newer version that is not in the pack.
- The OFFLINE_STYLE has no basemap, DEM or sprite (MapRoot.tsx:47-58), so offline trails and routes draw on plain dark ground. Hillshade and terrain are not packed. The research notes suggest the z12 terrarium tiles for a fire are about 6.8 MB and could serve both 3D terrain and routing, but that would be a new pack section.
- The packModel.ts header comment (6-10) is stale: it says weather frames are out of v1, but the plan now includes them (:192-212). Don't rely on header comments for the contents list.
- Open question: z/x/y tiles through an addProtocol shim need no new dependency and reuse sheetTileUrls, at the cost of about 1.5k files per fire for z8-14. A PMTiles file per fire is a single file but needs Range or custom-Source work plus a dependency. Per-fire GeoJSON is simplest offline and matches every existing overlay, but is heavier to render for dense areas. The planner should pick one.
