# worker

## Summary
The worker is one Python 3.12 package, `worker/responder_worker/`. Its single entry point is `python -m responder_worker.cli <subcommand>`. Subcommands are argparse subparsers (`cli.py:1501-1579`), each bound to a `cmd_*(args) -> int` function. The existing subcommands are sync-catalogs, sync-incidents, tile-worker, backfill, prune and cleanup-spread-frames. Every subcommand takes `common()` flags: `--dry-run`, `--out`, `--force`.

**Job shape.** A job does the following, in order:
- Records `job_started`.
- Builds storage with `make_storage(args.dry_run, args.out)`. Dry-run writes the exact B2 key layout under `worker/out/`.
- Loads the single `state/state.json` document (`state.py`).
- Opens the polite httpx client (`http.make_client`).
- Arms a module-global wall-clock with `frames.start_deadline(seconds)`, and loops while `frames.deadline_passed()` is false. Work is budgeted and resumable, and each item's failure is logged and skipped.
- Uploads in atomic order: immutable assets, then markers or manifests, then run catalogs, then `catalogs/catalog.json` last with a monotonic version.
- Saves state and publishes a best-effort heartbeat section with `health.publish(storage, job, entry)`.

**Storage (`b2.py`).** Uploads use boto3 against the B2 S3 endpoint. `put_object` handles bytes and `upload_file` handles files, which uses s3transfer multipart above 8 MB. Every put sets ContentType and CacheControl only, both derived from the key by `config.content_type_for_key` and `config.cache_control_for_key` (first matching prefix wins). There is no Content-Encoding support, no gzip handling and no list API; the only listing is inside `delete_prefix`. Multi-file uploads go through `put_tree`, which runs 8 threads.

**Immutability is by key design.** Keys that are never rewritten get `max-age=31536000, immutable`:
- incident tiles keyed by `sha16` of the source PDF;
- hotspot chunks under a generation prefix `g{N}`;
- run-stamped weather frames;
- versioned catalogs.

Mutable pointers get `max-age=60` or `300`.

**GDAL.** GDAL is used only through subprocess CLI: `gdalinfo -json`, `gdal_translate`, `gdalwarp`, `gdaldem`, `gdal_calc.py`, `gdal2tiles.py`, `ogr2ogr`, `ogrinfo`. There are no Python bindings, and numpy is not in the uv venv. Tools are checked with `shutil.which`. When GDAL is missing, the affected phase is skipped with a log line and a health note, never a crash. Each GDAL-using job's workflow installs apt `gdal-bin python3-gdal poppler-utils` in a bounded retry loop marked `continue-on-error`. CI logs show the runner is ubuntu-24.04 (image 20260920.314.1) with GDAL 3.8.4+dfsg-3ubuntu3.

**Tile pyramids.** The pattern is:
1. `gdal2tiles --xyz`, full grid, no `-x`.
2. `storage.put_tree("tiles/incidents/{slug}/{sha16}", dir)`.
3. Write a `meta.json` completion marker last.
4. Publish a manifest entry with `url_template "/tiles/incidents/{slug}/{sha}/{z}/{x}/{y}.png"` plus minzoom, maxzoom and bounds.

All URLs are root-relative, and the frontend prepends `VITE_DATA_BASE_URL` (https://f005.backblazeb2.com/file/responder-debrief-data).

**Parallel stateless pattern (tile-worker, `tile.yml`).** It uses:
- matrix shards, partitioned by `int(sha[:8],16) % shards`;
- read-only state;
- output of assets plus markers only;
- its own concurrency group.

An adopt job in the shared `worker-b2-writes` group then folds the markers into state and catalogs.

**Per-fire records.** `fires.fetch_active_fires` returns the active wildfires from `fire-api-prod /fires?active=true`; there are 312 today. Each record has:
- `fire_slug`: slugified `post_title`, with an order-dependent de-duplication;
- `cornea_id`, `unique_slug`, `unique_fire_id` (often null);
- `coordinates [lon,lat]`, state, acres, `created_on`, `poly_last_updated`.

There is no per-fire bbox or perimeter geometry in `catalog.json`. The only existing loop over all active fires with a bbox is the hotspot archive inside sync-catalogs (`cli.py:128-156`). It builds a box of the fire point ±0.6°/±0.5°, unions it with the forecast-run centroid, pads 20% and snaps to 0.25°. It stores the box in `state["hotspot_archive"][slug]` and in `hotspots/{slug}/index.json`, and runs stalest-first under a 240 s deadline.

Perimeters are touched only for version counts, via `fire-api-dev /fires/{cornea_id}/perimeters`. Bulk traffic must use the dev fire API.

**Two writer jobs.** `catalog.json` is rebuilt wholesale by both sync-catalogs and sync-incidents. Both run in the `worker-b2-writes` concurrency group because both read, modify and write `state.json` (4.5 MB, publicly readable) and `catalog.json`.

**Tests.** pytest, run locally only (no workflow runs pytest). They use real captured fixtures, monkeypatched stub clients and storages, `DryRunStorage(tmp_path)`, `httpx.MockTransport`, and skip GDAL-dependent tests when the tool is absent. All 204 pass in about 2 s.

**Implications for the two new jobs.** A weekly national trails-tiles job and a per-fire routing-bundle job fit best as:
- new modules with pure, unit-tested builders plus a `sync()` entry;
- new cli subcommands;
- new workflows modeled on `tile.yml`: their own concurrency group, stateless, writing assets, then a pointer or marker last.

They should publish their own pointer JSON, or be adopted into `catalog.json` through both writers. They also need new cache-control and content-type rules for their prefixes, and must avoid sparse z/x/y pyramids: B2 404s carry no CORS headers, and the offline pack assumes full grids.

## Conventions
- GDAL is used ONLY through subprocess CLI; there are no osgeo Python bindings and no numpy in the uv venv (geopdf.py:3-4, hrrr.py:12-13, spec-backend.md:7). GDAL output is parsed as text/JSON (gdalinfo -json; XYZ text in hrrr.parse_xyz_values 381-399). python3-gdal/numpy from apt exist only for system /usr/bin/python3 and are not importable from `uv run`.
- Check tools with shutil.which before use. A missing GDAL degrades gracefully: skip the phase, log '[tag] GDAL unavailable ...', and record gdal_available / a note in the health entry (cli.py:300-311, 910-912; hrrr.py:571-576). Per-item subprocess failures are caught, recorded as a short 'error' (last stderr line, ≤300 chars) and never kill the job (geopdf.py:288-294; hrrr.py:324-329).
- Every subcommand supports --dry-run (DryRunStorage writes the exact B2 key layout under worker/out/), --out and --force via common() (cli.py:1506-1512). B2 credentials are required only when not in dry-run (config.py:248-254).
- Logging: cli.log() is print(flush=True) with bracketed tags like '[catalogs]', '[hotspots]', '[tilew]'. Library modules accept a `log=print` parameter rather than importing the logger.
- Wall-clock first: arm frames.start_deadline(seconds) and check frames.deadline_passed() in every loop. Size the deadline so the job always reaches manifest/catalog/state uploads before the CI timeout (config.py:43-47 comment). Unfinished work is deferred to the next run through resumable state, never lost.
- Atomicity comes from upload ORDER, since B2 PUTs are atomic: immutable assets first, then markers and manifests, then run catalogs, then catalog.json LAST (catalogs.py:1-7, cli.py:288-294, plan.md:148). Completion markers are written after the tree (cli.py:937-943).
- An immutable Cache-Control is allowed ONLY for URLs the pipeline will provably never rewrite: content-addressed sha16, generation prefixes g{N}, run-stamped workspaces, versioned catalogs (hotspots.py:10-25; config.py:190-200). Mutable pointers use max-age=60 (catalogs/) or 300.
- JSON documents carry schema_version (or 'schema') and generated_at/updated_at, and use root-relative URLs ('/tiles/...', '/hotspots/...'); the frontend prepends DATA_BASE_URL (frontend/src/api/catalogs.ts:58-60). put_json writes indent=1, ensure_ascii=False (b2.py:28-31). The HRRR uv-grid JSON uses compact separators via put_bytes (hrrr.py:443-445).
- Politeness: one shared httpx client with a contact user agent (config.py:30), tenacity retries on transport errors, 429 and 5xx (http.py:27-51), and low concurrency (FRAMES_CONCURRENCY=2). Conditional GETs use If-None-Match/If-Modified-Since with 304 handling (mirror.py:316-333, archives.py:92-110). Bulk fire-API traffic goes to FIRE_API_DEV; prod serves only the light hourly index (config.py:13-17).
- Env overrides are wired explicitly: argparse defaults read os.environ (PRIORITY_FIRES cli.py:1540, TILEW_MAX_SECONDS 1556), inline os.environ.get with a config default (MIRROR_MAX_SECONDS 1183-1184, FRAME_BUDGET 76), or config helper functions (archive_base config.py:27-28).
- State is a single JSON document with per-feature sections added via state.setdefault(...) (e.g. perim_counts cli.py:95, hotspot_archive 129, ir 814). Only jobs in the worker-b2-writes concurrency group may write it or catalog.json.
- Retention policy: never auto-delete incident data. Deletion commands are manual-only and require an explicit --confirm (cli.py:1425-1434, 1478-1485).
- Workflows use odd-minute crons plus workflow_dispatch, concurrency with cancel-in-progress: false, a bounded GDAL apt retry loop marked continue-on-error (timeout-minutes 9), setup-uv@v5 with python 3.12, `uv sync`, and `uv run python -m responder_worker.cli ...` with defaults.run.working-directory: worker.
- Tests are pytest files named tests/test_<module>.py and use real captured fixtures from live sources (documented in each test module's docstring). Plain classes or functions, monkeypatch for clocks, constants and I/O, no network, GDAL tests skip-if-missing. Run locally with `cd worker && uv run pytest`; CI never runs them.
- Minimal dependencies (owner preference): prefer apt CLI tools and the stdlib over new PyPI packages. The current runtime dependencies are only httpx, lxml, rapidfuzz, boto3, tenacity and pypdf (pyproject.toml:6-13).

## Risks
- The catalog.json wholesale rebuild will drop new fields. Any per-fire 'trails'/'routing_bundle' field added to build_catalog must be derivable in BOTH cmd_sync_catalogs (cli.py:275-286) and cmd_sync_incidents (cli.py:1380-1386), from state or markers. Otherwise the other writer blanks it within the hour. A standalone pointer JSON (e.g. catalogs/trails.json, or routing/{id}/index.json per fire) avoids touching the writers.
- Concurrency and state clobbering: writing state/state.json or catalog.json from a new workflow outside the worker-b2-writes group will race sync-catalogs and sync-incidents (catalogs.yml:11-17). Prefer stateless jobs with their own concurrency group, their own private state doc (state/trails.json) and completion markers, the tile.yml pattern.
- Sparse vector-tile pyramids are the biggest risk. ogr2ogr's MVT directory output writes only non-empty tiles. B2 404s carry no CORS headers, so MapLibre gets console CORS errors, and packModel's full-grid enumeration would try to fetch missing tiles (packModel.ts:74-106). Options:
- a single-file PMTiles archive (B2 Range requests verified: 206 + Accept-Ranges) with a per-fire extract for the pack;
- writing empty tiles to fill the grid;
- publishing a tile listing and marking pack entries optional.
- Compressed tiles: GDAL's MVT writer gzip-compresses tiles by default (COMPRESS=YES creation option; verify on 3.8.4). B2Storage cannot set Content-Encoding (b2.py:135-139), and B2 does not compress on the fly (verified). Pre-gzipped .pbf without a Content-Encoding header will not parse in MapLibre. Either add ContentEncoding plumbing to b2.py, use -dsco COMPRESS=NO, or use PMTiles (the pmtiles client decompresses internally).
- Immutability and weekly rebuilds: new prefixes default to 'public, max-age=300' (config.py:211). A weekly rebuild that overwrites the same keys cannot be marked immutable. Use a build-id or content-hash prefix plus a short-TTL pointer JSON. B2 keeps prior file versions on overwrite unless bucket lifecycle rules say otherwise, and only catalogs/versions/ lifecycle is mentioned (README.md:91), so repeated national rebuilds accumulate hidden versions and storage cost.
- GDAL 3.8.4 limits:
- The unified `gdal raster|vector ...` CLI does not exist (it arrived in GDAL 3.11); use the classic ogr2ogr, gdalwarp, gdaldem and gdal_calc.py tools.
- The PMTiles vector-write driver was added in GDAL 3.8.0, and ESRIJSON FEATURE_SERVER_PAGING and OpenFileGDB read are available, but confirm the Ubuntu build with `ogrinfo --formats | grep -Ei 'pmtiles|mvt|esrijson|openfilegdb'` in the workflow before relying on them.
- Local dev uses brew GDAL, likely a newer version, so tests can pass locally on features CI lacks.
- Unreliable GitHub scheduling: 'hourly' crons currently fire every ~3-6 h (gh run list). A weekly cron may slip or be skipped. Add workflow_dispatch and make the job idempotent and catch-up-safe, e.g. a daily cron that no-ops when the published build is less than 7 days old. Remember that jobs killed by timeout-minutes report 'cancelled', not 'timed_out'.
- Runner budget: the hosted runner for a public repo is 4 vCPU, 16 GB RAM and a documented ~14 GB SSD. Free disk was NOT measured in these logs, so add a `df -h` step early. The job maximum is 6 h. National FGDB/FeatureServer pulls, OSM extracts, and LANDFIRE/DEM mosaics for many fires must be streamed to disk (http.get buffers whole bodies, mirror.py:335) and cleaned per fire with TemporaryDirectory.
- Per-fire scale: there are 312 active fires today, many tiny (NM 55, PR 17, OK 20); only 93 exceed 1,000 acres. The hotspot bbox can reach 2°x1.75° (crosswhite), about 34M cells at 30 m. The routing job needs an AOI policy (smaller than the hotspot box, or perimeter plus buffer), prioritisation (acreage, PRIORITY_FIRES, has_incident_maps), sharding (_sha_in_shard) and a skip-if-inputs-unchanged key such as poly_last_updated, a source build id and a recipe version.
- Unstable fire_slug: fire_slug comes from post_title and the de-duplication depends on API order (fires.py:79-87), so a new same-named fire can steal the bare slug. Key per-fire bundles by cornea_id or unique_slug, and record them. unique_slug is fetched (fires.py:30) but not exposed in catalog.json. unique_fire_id is often null.
- Perimeter access: the worker has no perimeter-geometry fetch today. The routing job must use FIRE_API_DEV (the bulk-traffic rule, config.py:14-17) and the verbatim 'path' from /fires/{cornea_id}/perimeters, which mixes CalFire keys; never reconstruct the URL.
- Health visibility: HealthView pulls only the 40 latest runs across all workflows and filters by name. A weekly workflow will usually scroll out of that window, and HealthDoc has no section for new jobs (types.ts:475-481). Use the per-workflow runs endpoint, or publish a health section via health.publish and add frontend support.
- Public bucket exposure: everything is publicly readable, including state/. Never store tokens or unpublished inputs there. Upstream API keys (if any are needed for LANDFIRE LFPS etc.) must come from GitHub secrets, not B2.
- Env wiring gotcha: env vars set in YAML do nothing unless the CLI reads them; for example TILE_BUDGET is dead (cli.py:1538). Wire new knobs explicitly via os.environ.get in argparse defaults or in config.
- More than 10 upload threads in put_tree will exceed boto3's default connection pool (10) and log pool-full warnings unless botocore Config(max_pool_connections) is set in B2Storage.__init__ (b2.py:128-133).
- Stale docs: README.md says the mirror runs 4x/day and that catalogs pre-render pyrecast frames, and spec-backend.md lists an old module set. Don't plan from them; the workflows and code are authoritative.
- Tests are not run in CI. New tests only protect the build if they are run locally, or if a pytest step is added to the new workflows.
- Worktree side effect: running `uv run --offline pytest` created gitignored artifacts in this read-only worktree (worker/.venv, worker/.pytest_cache, worker/responder_worker/__pycache__, worker/tests/__pycache__). My attempt to delete them was blocked by the permission classifier. They are gitignored (worker/.gitignore) and harmless, but the parent may want to remove them.
