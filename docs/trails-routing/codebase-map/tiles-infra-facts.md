# tiles-infra-facts

## Summary
Evidence gathered 2026-09-24 from the web, the repo, the live B2 bucket, a live Chrome 152 test from https://incibrief.com, and local GDAL 3.13.2 test builds on an M5 Pro. The GDAL runs used real USFS, NPS and BLM geometry pulled from the agency REST services into the scratchpad.

(1) GDAL. ubuntu-latest is still the ubuntu-24.04 image. The repo's own Tile worker run 36045681183 logged "Image: ubuntu-24.04, Version 20260920.314.1" and installed gdal-bin and libgdal34t64 3.8.4+dfsg-3ubuntu3. The Launchpad amd64 build log for that package lists "ogr_MVT, MVT" and "ogr_PMTILES, PMTiles" as enabled drivers, and it was built with GEOS and SQLite. MVT write needs both, so MVT directory/MBTiles writing and PMTiles writing are both available on the runner.
- Writing PMTiles in 3.8.4 is two steps. The MVT writer first writes `<out>.tmp.mbtiles`. It uses its own SQLite scratch database `<that>.temp.db`, which is deleted as soon as it opens on Unix, so it takes disk space but never shows in `ls`. Then the driver converts to a clustered PMTiles v3 file with gzip tile and internal compression and MD5 de-duplication.
- Options: MINZOOM/MAXZOOM are dataset options (`-dsco`, default 0/5), with per-layer overrides via `-lco` or the CONF JSON. SIMPLIFICATION and SIMPLIFICATION_MAX_ZOOM are in tile units. The layer name comes from `-nln`, `-lco NAME` or CONF `target_name`. All source fields are kept unless `-select` or `-sql` trims them. The MVT-only options (COMPRESS, TEMPORARY_DB, FORMAT, TILE_EXTENSION) are not documented for PMTiles.
- There is no density-based feature dropping. A tile over MAX_SIZE (500 kB compressed) is re-encoded at half the coordinate resolution (EXTENT) down to 256, then the smallest features are dropped. In 3.8.4 this only shows under CPL_DEBUG.

Measured locally (GDAL 3.13.2, 4 threads): about 150k simplified trail lines built in 29 s to z13 and 42 s to z14, and 286k in 66 s to z14. Memory stayed at 126–170 MB from GeoPackage input; a 37 MB GeoJSON input used 1.1 GB. Peak temporary disk was 1.8–4.4 times the output size for the scratch database plus about 1.2 times for the tmp.mbtiles. pmtiles verify and pmtiles extract both work on the GDAL-built archives.

(2) pmtiles on npm is at 4.5.0 (2026-08-10). It has one runtime dependency, fflate, and is 7.7 kB gzipped per Bundlephobia. It plugs into MapLibre with `new Protocol()` and `maplibregl.addProtocol('pmtiles', protocol.tile)`. The `Source` interface is two methods, `getBytes(offset, length, signal?, etag?)` and `getKey()`. `FileSource(File)` reads through `Blob.slice`, so an OPFS `FileSystemFileHandle.getFile()` result works directly. Register it with `protocol.add(new PMTiles(src))` and point the style at `pmtiles://<key>`. MapLibre workers hand custom-protocol requests to the main thread, so the loader always runs there.

(3) A single-range `Range: bytes=a-b` header is CORS-safelisted, so there is no preflight, in Chrome 99+, Firefox 117+ and Safari 16+. Suffix ranges and multi-range headers are not safelisted. pmtiles sends only `range`, and never If-Match. It needs Access-Control-Allow-Origin on the 206 response; Content-Length is safelisted. Exposing ETag is optional: it only enables detecting that the archive changed mid-session. Content-Range is read only when the archive is smaller than 16 kB.

(4) B2. The repo sets CORS only in README instructions (allowedHeaders ["range"], exposeHeaders ["etag","content-range"]); no code sets it. The live bucket echoes the Origin with credentials allowed and allows the `range` header in preflight. It answers If-Match preflights with 401. No Access-Control-Expose-Headers appeared on any response.
- Native f005 URLs return 206 with Content-Range, and 416 with a non-standard `Content-Range: */N`. A multi-range request gets a 200 with the whole file. They send no ETag or Last-Modified, speak only HTTP/1.1, and do not gzip on the fly.
- Content-Encoding is served from the `b2-content-encoding` file info or S3 ContentEncoding set at upload, per B2 docs and a Backblaze sample. I did not test this live.
- Live Chrome finding: repeated range requests to the native URL are not served from the HTTP cache (14–21 ms each). The same requests to the S3-endpoint URL, which sends ETag and Last-Modified, are cached (1–2 ms). Full 200 responses from the native URL are cached.

(5) The GDAL MVT directory writer gzips tiles by default (COMPRESS=YES; files start with the gzip magic bytes 1f 8b). MapLibre 5.24 does not decompress tiles; it throws "please make sure the data is not gzipped". The options are COMPRESS=NO (about 1.6 times the bytes), uploading with Content-Encoding: gzip, or an addProtocol loader that decompresses with DecompressionStream.

(6) The three agency trail sources total about 150k features: USFS 81k with geometry out of 86,417, NPS 31.5k, and BLM trail layers 37k. Adding BLM roads brings it to about 286k. About 600k is reached only if Forest Service or MVUM roads are added.
- Tile counts for the 150k trail features: 85,254 tiles for z7–z13 and 212,409 for z7–z14. For 286k: 105,323 and 271,675.
- Estimated archive size at full detail with about 11 attributes, trails only: about 160–290 MB for z7–z13 and about 240–430 MB for z7–z14. SIMPLIFICATION of 1–4 cuts 23–33%.
- A 50×50 km fire extract is about 0.4–2 MB.

## Extension points
- Worker upload: worker/responder_worker/b2.py:147 put_file. A single .pmtiles file is one upload; boto3 upload_file switches to multipart above 8 MB by default and B2 supports S3 multipart. Do NOT set ContentEncoding on .pmtiles, because a range request against a gzip-encoded object breaks. Only if you ship a gzipped z/x/y .pbf tree, extend _extra() at b2.py:135 to add 'ContentEncoding': 'gzip' for .pbf keys; put_tree at b2.py:46 then uploads per tile (85k–212k objects nationally per rebuild).
- worker/responder_worker/config.py:190 CACHE_CONTROL_RULES: add a prefix such as ('trails/', 'public, max-age=31536000, immutable') for a versioned key like trails/{build_id}/trails.pmtiles, referenced from a catalog/manifest written last, like the other immutable assets. config.py:214 CONTENT_TYPES: add '.pmtiles' (octet-stream is fine; I did not verify a registered media type) and '.pbf': 'application/x-protobuf' if a z/x/y tree is used.
- New weekly workflow: copy the GDAL apt retry block from .github/workflows/tile.yml:39-55 (gdal-bin 3.8.4 on ubuntu-24.04). Consider pinning runs-on: ubuntu-24.04 so a future ubuntu-latest flip to 26.04 (GDAL 3.12.2) is deliberate. Build step, via subprocess like the other GDAL calls: `ogr2ogr -f PMTiles out.pmtiles trails.gpkg -nln trails -dsco MINZOOM=7 -dsco MAXZOOM=13 [-dsco SIMPLIFICATION=1] [-dsco CONF=conf.json] -select <popup fields>`. Use GPKG or FlatGeobuf input, not GeoJSON (memory). Set GDAL_NUM_THREADS=4 on 4-vCPU runners.
- GDAL zoom and attribute split: put two OGR layers in the GPKG (for example trails_lo with a few fields or filtered features, and trails_hi with all popup fields). Map both to one MVT layer with CONF: {"trails_lo":{"target_name":"trails","minzoom":7,"maxzoom":10},"trails_hi":{"target_name":"trails","minzoom":11,"maxzoom":13}}. This is the pattern documented in the PMTiles and MVT driver docs for 3.8.4.
- Per-fire offline extract (worker side): either `ogr2ogr -f PMTiles fire.pmtiles trails.gpkg -spat w s e n -dsco MINZOOM=10 -dsco MAXZOOM=13` from the source GPKG (no new tool), or `pmtiles extract national.pmtiles fire.pmtiles --bbox=w,s,e,n --minzoom=10`. pmtiles extract is the Go CLI, not in apt; the GitHub release v1.31.2 Linux x86_64 tarball is 17.4 MB. Do not read PMTiles back with GDAL 3.8.4 (bug #9288, fixed in 3.8.5).
- Frontend registration: near frontend/src/main.tsx:40 (after installOfflineFetch), create one global `const protocol = new Protocol(); maplibregl.addProtocol('pmtiles', protocol.tile)`. The trails source is then `{type:'vector', url:'pmtiles://' + <B2 URL>}`. The pmtiles minzoom and maxzoom come from the archive header, and MapLibre overzooms past maxzoom.
- Offline pack: add an OPFS File accessor next to readPackFile (frontend/src/offline/opfs.ts:63), for example returning `(await dir.getFileHandle(name)).getFile()`. Then `protocol.add(new PMTiles(new FileSource(file)))` and use source url `pmtiles://<file.name>`, since FileSource.getKey() returns file.name. Alternatively implement a custom Source {getKey, getBytes} that reads OPFS and falls back to the network. Recreate the PMTiles instance after a pack update, because a File snapshot becomes unreadable once the file is rewritten.
- frontend/src/offline/packs.ts:125 installOfflineFetch must pass through any request that carries a Range header, or the .pmtiles URL must never enter urlIndex/prefixIndex. Otherwise, offline or on a slow network it returns the whole file with 200, and pmtiles FetchSource throws 'Server returned no content-length header or content-length exceeding request'. pmtiles calls the global fetch on the main thread, so the wrapper intercepts it.
- If z/x/y .pbf tiles are chosen instead: MapLibre fetches vector tiles inside its web worker (maplibre-gl-dev.js:9960-9975, 44504), so the window.fetch pack wrapper (packs.ts:125) never sees them offline. Offline vector tiles need a custom addProtocol scheme routed to the main thread, and that loader must return uncompressed bytes (gunzip with DecompressionStream if stored gzipped).
- Base URL: frontend/src/app/config.ts:7 DATA_BASE_URL is the native f005 URL. For browser HTTP caching of range responses, point the .pmtiles source at the S3-style URL https://s3.us-east-005.backblazeb2.com/responder-debrief-data/<key>, which sends ETag and Last-Modified and was cached in Chrome, for example through a new VITE_ variable. This works with the existing CORS rule (s3_get).

## Conventions
- Owner prefers minimal npm deps and Python/CLI tooling. pmtiles 4.5.0 adds one package plus one transitive dependency (fflate), about 7.7 kB gzipped. A no-dependency alternative is uncompressed z/x/y .pbf, but it costs roughly 85k–212k B2 objects per rebuild and needs a custom offline protocol.
- The worker calls GDAL as CLI tools via subprocess, installed by apt in workflows with a retry and mirror-fallback loop and continue-on-error (tile.yml:39-55, mirror.yml:44-65, catalogs.yml:42-57). Python is managed by uv (astral-sh/setup-uv@v5, python 3.12, uv sync).
- B2 keys follow a content-addressed or versioned immutable layout (tiles/incidents/{slug}/{sha16}/{z}/{x}/{y}.png with max-age 1y immutable). Mutable pointers (catalogs/*.json, 60 s must-revalidate) are uploaded last because upload order is the atomicity mechanism (docs/plan.md:148). Cache-Control and Content-Type are set per key prefix from config.py rules on every put.
- Storage is abstracted behind Storage/B2Storage/DryRunStorage (worker/responder_worker/b2.py). The dry run writes to worker/out/ with the exact B2 layout and needs no secrets. Worker tests are pytest against tests/fixtures; frontend tests are vitest with *.test.ts beside the source.
- Offline packs live in OPFS at packs/{slug}/{sha256(url)[:16]}[.ext] with a pack.json index (frontend/src/offline/opfs.ts). They are served through the window.fetch wrapper, network-first online and pack-first offline, with 8 s network patience.
- Workflows use concurrency groups; B2 writers serialize in the worker-b2-writes group. Secrets are B2_KEY_ID and B2_APP_KEY; vars are B2_S3_ENDPOINT and VITE_DATA_BASE_URL; bucket responder-debrief-data (endpoint region us-east-005 per live URLs, not the us-west-004 README example).
- Per memory notes: use the dev API for backfills, and preview needs a static build (the dev server cannot launch from ~/Desktop).

## Risks
- The native B2 URL (the current DATA_BASE_URL) sends no ETag and Chrome did not cache its 206 responses. A pmtiles archive served from there is re-fetched from the network every session (MapLibre keeps only an in-memory tile cache), and pmtiles cannot detect the file being replaced. Use immutable versioned keys (for example trails/{yyyymmdd or sha}/trails.pmtiles) referenced from a catalog, and consider the S3-style URL, which Chrome did cache. Safari and Firefox caching were not tested. pmtiles forces cache:'no-store' on Windows Chromium regardless.
- The live bucket sent no Access-Control-Expose-Headers, although the README rule lists exposeHeaders [etag, content-range]. I could not read the live rule without credentials; check with `b2 bucket get responder-debrief-data`. pmtiles works without it, but ETag change detection is off.
- Never set Content-Encoding (gzip) on the .pmtiles object: range reads against an encoded object break. PMTiles already gzips each tile internally. A z/x/y .pbf tree from GDAL is gzipped by default and needs either COMPRESS=NO (about 1.6× bytes), ContentEncoding=gzip on each upload (b2.py _extra does not set it today), or a gunzip-ing custom protocol. Otherwise MapLibre 5.24 throws the 'data is gzipped' error.
- The offline pack fetch wrapper (packs.ts:125) ignores Range and returns whole files with 200. If a .pmtiles URL is ever indexed, pmtiles throws. Separately, MapLibre fetches http(s) vector tiles inside its worker, which bypasses window.fetch, so the existing wrapper cannot serve z/x/y .pbf offline. Use pmtiles with FileSource or a custom Source, or a custom addProtocol scheme.
- GDAL 3.8.4 keeps every feature at every zoom and degrades oversize tiles silently: it halves EXTENT, then drops the smallest features, logging only under CPL_DEBUG before 3.10.1. With BLM roads or 600k features at full detail, z7–z9 tiles may hit the 500 kB MAX_SIZE. Mitigations: start the full-attribute layer at z9–z10, use CONF to split a sparse low-zoom layer from a detailed high-zoom layer, apply SIMPLIFICATION, set MAX_SIZE explicitly, or use tippecanoe 2.49 from apt, which has proper overview dropping.
- Build time for the full-detail national set on a 4-vCPU runner with GDAL 3.8.4 was not measured. Local GDAL 3.13.2 on an M5 Pro took 42–66 s for simplified geometry and about 4 s per 5.6k full-detail lines; the OurHike data point is 170 s for 143k lines at z5–14. Expect several minutes to a few tens of minutes and set a generous timeout-minutes.
- Temporary disk: the hidden SQLite temp DB was 1.8–4.4× the output, plus tmp.mbtiles about 1.2× the output, plus the output itself. For a 250–450 MB archive expect roughly 1–3 GB peak, within the runner's 14 GB. Use GPKG or FlatGeobuf input: GeoJSON input loaded everything into memory (1.1 GB RSS for 37 MB).
- ubuntu-latest will eventually move to ubuntu-26.04 (label already exists), which ships GDAL 3.12.2, a silent 3.8.4 → 3.12 jump. Pin runs-on: ubuntu-24.04 or test both.
- Do not use GDAL 3.8.4 to read PMTiles back (for example to cut per-fire extracts from the national archive): bug #9288 (fixed in 3.8.5) rejects some valid files. Build per-fire files from the source GPKG with -spat, or use the go-pmtiles CLI, which is not in apt and needs a GitHub release download.
- The USFS EDW service reloads in place: I saw counts rise from 34k to 86k over about 5 minutes on 2026-09-24. A weekly pull that overlaps a reload publishes a partial dataset. Guard with a count sanity check against last week, or use the weekly FGDB zip, which is atomic. About 6% of USFS records have null geometry.
- NPS includes territories (American Samoa, Guam), so GDAL writes header bounds of -170.77..145.73 and a meaningless center of (-12.5, 27.0). Filter the extent or accept it. GDAL writes MBTiles-style metadata; pmtiles' Protocol builds its own TileJSON from the header, so this matters mainly for the center and bounds.
- B2 is HTTP/1.1 only, so browsers open at most about 6 parallel connections per host. Each tile is one range request after the first 16 KB header/root read and occasional leaf-directory reads; initial render at a new location may feel slower than an HTTP/2 CDN.
- Egress is free only up to 3× average monthly stored bytes. A 250–450 MB archive viewed by many users adds egress; versioned weekly archives also need a lifecycle rule to delete old versions.
- A z/x/y tree means 85k (z7–13) to 212k (z7–14) objects per national rebuild through put_tree's per-file uploads. Upload throughput was not measured (likely tens of minutes), and old tiles need pruning. A single PMTiles file is one upload.
- Not verified: B2 serving Content-Encoding live (docs only); whether GDAL 3.8.4 accepts TEMPORARY_DB or BOUNDS for the PMTiles driver; Safari and Firefox HTTP caching of B2 206 responses; exact GDAL 3.8.4 output sizes (measured with 3.13.2, same writer design); whether gzip output from GDAL is byte-deterministic between builds (matters for skipping unchanged tiles in a z/x/y upload).
